
## MongoDB Transaction, 언제 사용하는가?
### RDB와 달리 필수 기능은 아님
- MongoDB도 RDB처럼 트랜잭션을 제공하긴 하지만, **MongoDB는 RDB와 설계 철학이 매우 다른 만큼 성능 및 유연성, 복잡도 면에서 고려 사항이 많다.**
- 데이터를 정규화함에 따라 여러 테이블에 데이터가 분산되는 RDB와 달리, MongoDB는 단일 document에 필요한 데이터를 모두 몰아넣어 하나의 doc만 생성/업데이트하는 것을 권장하기 때문에 일반적인 상황이라면 Transaction이 필요가 없다. (공식문서에서도 트랜잭션 필요성을 최소화 하는 방향을 권장)
### 그러면 언제 사용하는가?
- 문서 간 강결합이 존재할 때, 즉 **여러 doc의 생성/업데이트가 원자적으로 이루어져야 할 때** 사용
	- 계좌 A에서 금액을 차감, 계좌 B에 금액을 더하는 작업
	- 주문이 생성됨과 동시에 여러 상품의 재고 컬렉션에서 수량을 차감

## 동작 원리
### 먼저 알아두어야 할 것
- MongoDB Server는 각 클라이언트의 연결 단계에서 논리적 세션을 생성하며, 해당 세션에서 트랜잭션을 시작하면 고유한 Transaction ID를 부여한다. 이를 통해 트랜잭션에 포함되는 명령 여부를 구별한다.
- 트랜잭션을 시작하면 WiredTiger는 해당 시점의 논리적 스냅샷(view)을 생성하고, 커밋 시점에 이 스냅샷을 기반으로 변경 사항을 결정하는 MVCC 기반 동시성 관리 방식을 사용한다.
### 동작 흐름
1. **스냅샷 획득 및 트랜잭션 시작**: 트랜잭션이 시작되면 WiredTiger는 스냅샷을 생성한다. 이후의 모든 (트랜잭션 내) 읽기 작업은 이 시점의 데이터만 읽어 온다.
2. **변경 사항 버퍼링 및 Document Lock 획득**: 트랜잭션을 시작한 세션으로부터 들어온 변경 쿼리는 WiredTiger의 인메모리 캐시에 기록(buffering)해둔다. 그리고 변경 쿼리의 발생 시점에 Document Level의 Lock을 걸어 다른 트랜잭션이 해당 문서를 수정하지 못하게 막는다.
3. **Write Conflict 검증**: 변경 쿼리 발생에 의한 Document Level Lock 획득 시도 시점에, 스냅샷 시점 이후에 다른 트랜잭션에 의해 이미 데이터가 수정되었음이 발견되면 WriteConflictException을 발생시켜 트랜잭션을 Abort 처리한다.
4. **Commit 수행**: 3번의 검증이 문제 없이 통과했다면, 쿼리를 버퍼링하고 커밋 요청이 들어온 시점에 인메모리 캐시에 버퍼링한 변경 사항들을 디스크의 저널 로그와 Oplog에 기록하고 Document Lock을 해제한다. 이 시점부터는 트랜잭션 밖에서도 변경 사항을 볼 수 있게 된다.

## RDB Transaction과의 차이점

|                        | RDB                                                                                                        | MongoDB                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 설계 철학의 차이              | 정규화가 기본 데이터 스키마 설계 원칙이므로 한 번에 여러 데이터를 업데이트하는 일이 잦고, 이에 따라 Transaction을 주로 사용하게 되고 트랜잭션 처리에 최적화된 아키텍처를 가진다. | 하나의 document에 필요한 모든 정보를 내장하는 것이 스키마 설계 원칙으로, 해당 데이터만을 CRUD 하여 요청을 처리하는 것을 권장하므로 Transaction 없이도 대부분의 상황에 대응할 수 있다. RDB의 Transaction에 비해 성능 오버헤드가 크다. |
| 락 범위                   | Row, Page, Table 단위의 다양한 락을 지원한다.                                                                          | Document 단위의 락만 지원한다.                                                                                                                                 |
| 격리 수준(Isolation Level) | Read Committed, Repeatable Read 등 다양한 격리 수준을 지원한다.                                                         | 스냅샷 기반의 단일 격리 수준(Snapshot Isolation)만을 제공한다.                                                                                                          |

## 주의사항, 한계점
- Transaction 내부에서 컬렉션 생성, 인덱스 생성과 같은 DDL은 지원하지 않으며 CRUD만 가능하다.
- Transaction을 너무 크게 만들지 말 것. 진행 시간 동안 Document Level Lock이 걸린다는 점, 한 번에 Transaction의 모든 명령이 `oplog`에 기록되므로 이 내용이 복제 노드에 반영될 때 복제 지연을 유발할 수 있다는 점에 주의.
