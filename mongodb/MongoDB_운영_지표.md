
## CPU
- MongoDB에서 CPU의 사용처는 아래와 같이 분류됨
	- `user`: 주요 사용처로, MongoDB 프로세스가 사용하는 CPU 비율로, 쿼리 실행, 데이터 정렬, 압축 등에 사용
	- `system`: 커널 공간에서 실행되는 프로세스가 사용하는 CPU 비율로, 컨텍스트 스위칭이나 I/O 처리 등에 사용
	- `iowait`: CPU가 Disk I/O가 완수되기를 기다리는 대기 시간의 비율. RAM 부족에 의한 디스크 병목 여부를 판단할 수 있음
	- `steal`: 클라우드(가상화) 환경에서 다른 VM에 CPU를 빼앗긴 시간의 비율
- 각 타입별 CPU의 증가가 의미하는 바는 아래와 같음
	- `user`: 인덱스 누락에 의한 풀 스캔, 비효율적 쿼리, 또는 그냥 요청이 너무 많아 커넥션이 폭증
	- `system`: 과도한 컨텍스트 스위칭. 너무 많은 커넥션 또는 스레드가 있어 경합이 발생
	- `iowait`: 쿼리는 많은데 RAM이 모자라 디스크를 너무 자주 읽어, Disk 처리 속도가 MongoDB 요청 속도를 따라가지 못하는 상황

## Memory
- 메모리는 캐시 용도로 사용한다.
- 캐싱하는 건 무엇? '자주 조회되는' 데이터, '방금 변경된' 데이터, 그리고 **인덱스**
### 메모리 구조
- MongoDB에서 Memory를 어떻게 사용하는지 이해하려면 MongoDB의 메모리 구조를 먼저 이해해야 함
#### WiredTiger Cache
- (Total RAM - 1GB) / 2 만큼의 크기를 할당하며, 1차 캐시 역할을 한다.
- 데이터를 압축하지 않은 상태로 보관하며 가장 빠르게 데이터를 반환한다.
- Clean Page와 Dirty Page로 분류된다.
	- Clean 페이지에는 디스크와 동기화된, 디스크로부터 읽어온 데이터들이 캐싱된다.
	- Dirty 페이지에는 아직 디스크에 반영되지 않은 쓰기(생성/수정)가 캐싱된다.
- Dirty 페이지는 'Evict' 전 반드시 디스크에 반영되어야 한다.
	- Dirty 페이지는 5%까지는 특정 interval에 따라 or 저널 로그 크기 임계점에 따라 (백그라운드 스레드를 통해) 디스크에 반영된다.
	- 쓰기 속도가 너무 빨라 Dirty 페이지가 총 캐시의 5%를 초과하면 백그라운드 스레드들은 Dirty 페이지를 모두 디스크로 쓰기 시작한다.
	- 총 캐시의 20%를 초과하면 쿼리 처리를 멈추고 애플리케이션 스레드까지 동원해 디스크 반영에 집중한다.
#### OS Filesystem Cache
- 나머지 메모리 공간으로, 2차 캐시 역할을 한다.
- 데이터를 압축하여 보관하며 WiredTiger 캐시보다는 느리지만 Disk보다는 훨씬 빠르게 데이터를 반환한다.
### 캐시 타입
- `resident`: MongoDB 프로세스가 실제로 사용하는 메모리 크기 (제일 중요)
- `virtual`: 프로세스가 OS에 요청한 가상 메모리 공간. 부정확한 지표
- `WiredTiger Cache (used/free)`: WiredTiger 캐시 사용량/가용량

## 그 외 지표
### Query Targeting (Scanned / Returned)
- 스캔한 데이터 / 반환한 데이터 결과값으로, 클수록 데이터를 비효율적으로 탐색한다는 것
- 1000보다 작을 것을 권장
## Replication Lag
- Primary의 변경이 Secondary로 반영되는 시간이 느리다는 것
- 이 지표가 늘어난다면 Secondary의 성능이 부족하거나 Primary에서 대규모 쓰기 작업(Bulk Write)이 발생하여 Oplog 처리가 밀리고 있다는 뜻이다.
### Available Tickets (Read/Write Tickets)
- 동시성 제어를 위해 사용하는 읽기/쓰기 티켓
- 티켓 수가 0에 수렴한다면 쿼리들이 병목에 의해 큐에 쌓이고 있다는 의미
### Current Connections
- 현재 연결된 커넥션 수로, 연결 폭증이나 커넥션 누수를 알 수 있음
